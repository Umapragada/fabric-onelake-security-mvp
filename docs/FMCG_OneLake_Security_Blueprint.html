1 · Use case

KDD: one security definition for procurement and payables data

Illustrative learning scenario. KDD's public profile (products, markets) is real; its ERP setup, operating units, people and figures here are assumptions for the lab and do not describe KDD's actual systems.

Business context

KDD, founded in 1962, is the market leader in dairy in Kuwait. It makes dairy products, ice cream, natural juices and fruit drinks, and culinary products, and exports across the Middle East, including Saudi Arabia, Iraq, Bahrain, UAE, Qatar, Oman, Lebanon, Jordan, and India.

In this lab KDD runs Oracle EBS R12 with three operating units: 101 Kuwait (KWD, three-decimal fils amounts), 102 Saudi Arabia (SAR) and 103 UAE (AED). It is moving procurement and payables reporting to Microsoft Fabric.

What each domain buys and pays for

  • Procurement milk powder and raw milk, fruit concentrates, cocoa and sugar, aseptic cartons and PET bottles, cold-chain logistics. Item categories: Dairy, Ice cream, Juices, Culinary, Raw materials, Packaging.
  • Payables invoices from local and European suppliers, payment schedules, payments in three currencies, and supplier bank accounts (IBAN).

The problem

  • Analysts get whole-workspace access, so a Kuwait buyer can see Saudi purchase prices and an AP clerk can see supplier IBANs.
  • Grants are added by hand, rarely removed, and nobody can show who approved them.
  • Copilot, data agents and Foundry agents are arriving; each could expose data in its own way.

Goal

Define security once, as metadata, and have it applied automatically to every engine that reads OneLake. Every grant is approved, time-limited, mailed, audited and revoked on time.

Value

  • One place to change security: a row, not clicks in four tools.
  • Least privilege by row and column.
  • Evidence for internal audit.
  • AI tools inherit the same rules.

Business rules

  1. Buyers: POs, receipts and supplier names for their own operating unit only. No VAT number, no Payables.
  2. Planners: quantities and dates for their operating unit. No unit_price or po_value.
  3. AP clerks: invoices and payment status for their operating unit. No bank accounts, no Procurement.
  4. Treasury: payments and bank accounts for all operating units. No Procurement.
  5. Auditors: both domains, all operating units, minus bank account, IBAN and VAT columns. Always short-term.
  6. Bronze (raw EBS) is restricted to data engineers and auditors.
  7. Every grant has an end date, capped by the role's MaxDays.
  8. Leavers are revoked on the next daily run.
  9. No manual role edits; drift is detected and reported.

Acceptance criteria

  • All six personas get exactly the access in section 9, on all eleven surfaces in section 8.
  • No business user can see WS-SEC-Control, the metamodel, the pipeline or the admin report.
  • Every grant, revoke and role change has an AuditLog row with before and after JSON.
  • Every state change has a NotificationLog row with status Sent.
  • A revoke takes effect on the next run with no manual step.
  • DefaultReader does not exist on any secured lakehouse.

Out of scope

  • Live Oracle EBS connection (data is simulated).
  • Filtering workspace Admins, Members, Contributors (by design).
  • Copilot and data agent tests on trial capacity (needs F2+).

2 · Architecture

Bronze, Silver and Gold per domain, one hidden control plane

Each domain has three layer workspaces. Business users only ever hold the Viewer role on Gold; data stewards and auditors read Silver through OneLake roles; Bronze is for data engineers only. The security workspace has Admins from the security team and a service principal. Nobody else is in it, so it does not appear in their workspace list or the OneLake catalog.

Procurement Payables Bronze: raw EBS Silver: cleaned, conformed Gold: star schema for consumers Security control plane (dashed = writes roles, groups, mail)

Four access layers, one source of truth

  • RBAC: Viewer on WS-*-Gold for consumer groups, on WS-*-Silver for steward and auditor groups.
  • OLS: role Path lists only the tables the role may read.
  • RLS: role row constraint, WHERE org_id = 102.
  • CLS: role column constraint lists allowed columns.

Why the workspace stays hidden

A Fabric workspace is visible only to people holding a workspace role or an item share. The control plane has no Viewer, Contributor or shares. Fabric administrators can still see it in the admin portal; that is expected and cannot be switched off.

Why groups, not users, in roles

OneLake roles reference Entra groups. Granting or revoking a person is a Graph membership change, so role JSON only changes when a new scope (a new OU or role type) appears. Fewer role rewrites, smaller blast radius.

Bronze · LH_*_Bronze

EBS tables exactly as landed, all strings, plus load date and file name. Data engineers only; no OneLake roles needed.

Silver · LH_*_Silver

Typed and deduplicated, EBS codes decoded (status flags, payment terms), amounts in source currency plus KWD, supplier history as SCD Type 2. Tables keep EBS grain, for example silver.po_line, silver.invoice, silver.supplier. Stewards and auditors read it through OneLake roles with RLS on org_id.

Gold · LH_*_Gold

Star schema built for reporting and AI. Every business persona, semantic model and data agent reads Gold.

Gold then builds dim_supplier, dim_item, dim_org, dim_date, fact_purchase_order, fact_receipt (Procurement) and fact_invoice, fact_payment, dim_bank_account (Payables), keeping org_id on every fact.

4 · Security metamodel · SQLDB_SecMeta, schema sec

You maintain the first three groups. The sync engine writes the last two. Sample data script 05_SEC_Metamodel_Sample.sql seeds 15 people, 8 role templates, 16 requests in every status, 12 compiled role bindings, 5 sync runs, 61 audit rows and 17 notifications. PK primary key, FK foreign key.

4b · Entity relationships and data flow

How a request travels through the metamodel

Solid lines are table relationships (1 to many). Orange numbered lines are the data flow for one grant, UC-1. Dashed boxes are outside the database.

  1. Request

    The form writes an AccessRequest row for Data Steward, PrcBuyer, scope 102, Pending. The approval card flips it to Approved.

  2. Compile

    NB_SEC_Sync joins the request with RoleTemplate, ScopeValue and the three rule tables, and writes or updates RoleBinding PrcBuyerOU102 with its RoleJson.

  3. Groups

    Graph adds Data Steward to grp-ol-PrcBuyerOU102, the group named in RoleBinding.

  4. Roles

    RoleJson for every binding on LH_PRC_Gold goes out in one PUT to dataAccessRoles.

  5. Evidence

    One SyncRun row for the run, AuditLog rows for the membership change and any role change.

  6. Mail

    A NotificationLog row of type ENABLED is sent through Outlook and marked Sent.

  7. Report

    The views read AccessRequest, RoleBinding and AuditLog; RPT_SEC_Admin shows Data Steward's access and its end date.

Three rules the compiler must obey. (1) The PUT replaces the item's whole role set, so the engine always sends every role for that lakehouse; anything missing, including DefaultReader, is deleted. (2) RLS predicates are static, so one role per scope value: PrcBuyerOU101, PrcBuyerOU102, PrcBuyerOU103. (3) Keep a table's RLS and CLS in the same role, and avoid putting one person in two roles that secure the same table differently.
6 · Sync engine · NB_SEC_Sync, run by PL_SEC_Lifecycle

Desired state in, reconciled platform out

  1. Trigger

    Daily at 06:00, and on demand after an approver sets a request to Approved.

  2. Read desired state

    Active grants are approved requests where today is between StartDate and EndDate and the user's EmploymentStatus is Active.

    SELECT … FROM sec.AccessRequest JOIN sec.UserProfile …

  3. Reconcile Entra groups

    Create a missing group per role binding, then add and remove members so the group matches the grants exactly.

    Graph: POST /groups · POST /groups/{id}/members/$ref · DELETE …/members/{id}/$ref

  4. Compile and diff

    Build each lakehouse's full role set as JSON, hash it, compare with the last applied hash and the live roles from GET. Unchanged items are skipped.

    GET /v1/workspaces/{ws}/items/{lh}/dataAccessRoles

  5. Dry run, then apply

    Send the body with dryRun=true first to catch validation errors, then apply with the ETag in If-Match so a manual edit made in between is detected, not overwritten.

    PUT /v1/workspaces/{ws}/items/{lh}/dataAccessRoles?dryRun=true → PUT (If-Match)

  6. Workspace RBAC

    Make sure each consumer group holds Viewer on the domain's Gold workspace and nothing more.

    POST /v1/workspaces/{ws}/roleAssignments

  7. Write evidence

    One SyncRun row, one AuditLog row per grant, revoke or role change with before and after JSON.

  8. Queue and send mail

    Insert NotificationLog rows, then the pipeline's Office 365 Outlook activity sends them and marks each Sent or Failed.

  9. Refresh admin report

    RPT_SEC_Admin reads the views; only the security team can open it.

7 · Access lifecycle and mail alerts

Every grant has an end date

Requested

Row in AccessRequest, Status Pending. EndDate is capped at the template's MaxDays.

To approver: request waiting

Active

Approved and StartDate reached. Next sync adds the user to the group.

Access enabled to user, cc manager: role, scope, end date

Expiring

Seven and one day before EndDate.

Expiry alert T-7 and T-1 to user and approver, with how to extend

Extended

Approver moves EndDate. Audit row records old and new date.

Extension confirmed to user

Revoked

EndDate passed, manual revoke, or user marked Leaver. Removed from group on the next run.

Access revoked to user, cc manager and security team

A revoke takes effect when the user is removed from the Entra group. Allow a short delay before the change reaches every engine, and test it explicitly in phase 7.

From a request to what every engine shows

Read left to right. Numbers follow one request. Badges show what is live today (green), what runs as an MVP stand-in (amber) and what is still to do (red).

Control planeIdentityDataEvidence and auditOrange arrows: run by the daily pipeline

What one request does

Emma Clarke asked for Procurement buyer on OU 101 (ACC-00017). After approval the next run made the request Active, added her to grp-ol-PrcBuyerOU101, and the PrcBuyerOU101 role on LH_PRC_Gold already lists that group. She now sees Kuwait purchase orders only, until 21 Dec.

What stops bad grants

Before anything is applied, the lifecycle step rejects requests that break the role's maximum days, use the wrong scope type, or clash with a role the person already holds (for example buyer and AP clerk on the same unit).

What makes it safe to rerun

Every run compares the wanted roles with the live ones. Unchanged lakehouses print "no change"; a hand-edited role is reported as drift and left alone unless you force it.
